## Human review UX

- Added `review_processed_visibilities` as a Prefect task using `pause_flow_run`.
- Changed the task input from an observation ID to an `Observation`, allowing a process future to be passed directly into the review task.
- The task validates that processing reached `AWAITING_REVIEW` and that the processed-data directory exists before pausing.
- Identified `main.py`, not `review.py`, as correct place to act on a review decision — orchestration belongs at flow level.
- Paired each `process_future` with its `review_future` instead of tracking review futures alone, so the resolved observation stays available after `.result()`.
- On CONTINUE: submit `remove_ms` to delete the `.ms` dir. On REPROCESS: resubmit `process_visibilities` then `review_processed_visibilities`, mirroring the original receive-loop chaining pattern, not a bare fire-and-forget process call.
- Added `resolve_review_cycle()` looping REPROCESS until CONTINUE or a configured attempt cap (`config.quality_gate.max_attempts`, new field, default 2). On cap hit or unexpected/timed-out decision, log a warning and leave the `.ms` dir in place rather than retrying indefinitely (later revisited — see Bug fixes).
- Function later relocated from `main.py` into `src/sdp_control/tasks/review.py` (co-located with `ReviewDecision` and `review_processed_visibilities`); `main.py` now just imports and calls it.
- Added observation ID and a link to the preview artifact directly in the Prefect "Resume Flow Run" modal: a custom `ReviewDecisionInput(RunInput)` subclass with `with_initial_data(description=...)`, since a bare `RunInput` doesn't carry any description into the UI. `create_preview_artifact` changed to return the artifact's UUID (previously discarded) so its URL could be built and linked.
- Added a `logger.warning("⏸️ PAUSED — ...")` line and a best-effort Slack notification (`_notify_review_needed`, wrapping a `SlackWebhook` block named `sdp-review-alerts`) right before `pause_flow_run`, so a reviewer doesn't need to be watching the UI to know a review is waiting. Both the artifact link and `PREFECT_UI_URL` are included in the Slack message. Designed fail-open on purpose: `review_processed_visibilities` already has `retries=3`, so an unhandled Slack failure would otherwise retry the whole task (re-generating the preview artifact) before ever reaching the pause.

## Storage management

- Verified from Prefect logs that a configured limit of 2 prevents a third process from acquiring a slot; blocked attempts receive `423 Locked` until a slot is released.
- Diagnosed a concurrent-pause crash regression from a similar mechanism missing on the review-pause path (`pause_flow_run` pauses the whole flow run, not just the calling task) and added a matching `review-pause` global concurrency limit (fixed at 1) to serialize review pauses, including reprocess-triggered re-reviews.
- Explained (diagnostic, no code change) why the original campaign loop would stop outright once `storage_threshold_mb` was crossed even if space would free up shortly after, tracing the exact `main.py` lines responsible for the one-shot `break`.
- Replaced the hard `break` on storage-full with a wait-and-retry loop: polls indefinitely by default (`observation.storage_wait_indefinite: true`) or up to `observation.retry_attempts` if capped, rechecking storage on a `retry_delay_seconds` interval (real disk rescan each time, since `get_total_ms_size_mb` always reflects live state).
- Added `storage.count_scope` (`ms_only` vs `all`) so the threshold can count either just raw `.ms` dirs or everything under `data_dir`, including processed/preview output.
- **Self-introduced regression, caught and fixed**: the wait-and-retry change created a deadlock — `resolve_review_cycle` (which frees space via `remove_ms`) was only submitted in a post-loop cleanup block reached after the loop's `break`, but with indefinite waiting the loop never reached that `break` unless space freed, which required `remove_ms` to have already run. Diagnosed from a pasted flow-run log showing "Still over threshold" retrying 20+ times with zero space freed despite logged "continue" decisions. Fixed by moving `resolve_review_cycle.submit(...)` inline into the receive loop, per observation, so cleanup runs concurrently regardless of whether the loop is currently sleeping in its storage-wait branch.
- **Real bug found and fixed**: `storage_full()` and `get_total_ms_size_mb()` both accepted override parameters (`storage_threshold_mb`, `storage_count_scope`) meant to let `main.py`'s flow parameters (settable from the Prefect UI) override the YAML defaults — but their function bodies ignored the parameters and re-read `config.storage.*` directly, silently discarding any UI-set value. Confirmed via a screenshot of the flow run's Parameters tab showing the correct value reaching `main()`, while the log still reported the old threshold. Fixed both functions to use the passed-in parameter instead of the global config.
- Added `observation.storage_wait_safety_limit` — a hard ceiling on wait-retries even when `storage_wait_indefinite: true`, as a last-resort guard against a deadlock of the same shape recurring in the future; `main.py`'s retry loop condition restructured (`while attempt < retry_attempts or (indefinite and attempt < safety_limit)`) so the loop's give-up branch is always reachable.
- Discussed (design question, no code yet): whether quality-gate-exhausted observations should also be quarantined, not just have their raw `.ms` kept in place. Diagnosed that under `count_scope: all`, leaving processed-output directories behind would keep counting toward the threshold even after the raw `.ms` was handled — reopening the same class of deadlock under that scope.
- On quality-gate exhaustion: mark the observation `FAILED` and move (not delete) both the raw `.ms` and every reprocess attempt's output directory into a new `storage.failed_dir`, via a new `quarantine_ms` task. Living outside `data_dir` means both `count_scope` modes naturally exclude it from the threshold count with no extra filtering logic.

## Bug fixes

- Diagnosed from a Prefect log CSV (`thistle-mantis.csv`) that the first review only started after the *last* receive task, not right after its own process task finished. Root cause: a review loop placed after the receive loop was gated behind all receives finishing. Fixed by submitting review inside the receive loop with `review_processed_visibilities.submit(process_future, wait_for=[prior_review_future])`.
- **Stale preview on reprocess (real bug, found via a general question, not reported by user)**: `observation.datetime_stamp` is set once at campaign start and the same `Observation` is resubmitted on reprocess, so every reprocess attempt built the identical processed-output path. `create_preview_artifact` only regenerated `previews.png` if it didn't already exist — so after attempt 1, a reviewer evaluating attempt 2 was silently shown attempt 1's stale image. Fixed by adding `Observation.processing_attempt` (default 1, incremented by `resolve_review_cycle` on each reprocess) and suffixing every processed-output path with `_attempt{N}` across `process_vis.py`, `preview_artifact.py`, and `review.py` — this also means prior attempts are now preserved on disk instead of being overwritten in place.
- Diagnosed a `main.serve()` `httpx.ConnectError` reported when running without `prefect server start`: the user's local Prefect CLI profile has `PREFECT_API_URL` set, so Prefect skips its ephemeral in-process API fallback and tries to reach a real server that wasn't running.
- Flagged (not fixed at the time; fixed later during integration-test work) that an externally-added `SlackWebhook(...).save(...)` call at module import time in `review.py` would crash any import of that module — including plain `pytest` collection — if `PREFECT_SLACK_WEBHOOK_URL` wasn't set. Fixed by moving the registration into a lazy `_ensure_slack_block()`, called only from inside `_notify_review_needed`'s existing fail-open `try` block.
- While writing a unit test for `_notify_review_needed`'s fail-open behavior, discovered it isn't itself a `@task` — calling it directly (as the new test did) has no Prefect run context, so `get_run_logger()` raised `MissingContextError`. Not a production bug (it's always called from within `review_processed_visibilities`'s task context in real use), but fixed the test to patch the logger rather than leaving a misleading failure.

## Kubernetes runner (design artifact)

- Guided step-by-step through building `k8s_runner.py` to match `docker_runner.run_container`'s exact interface (`run_container(image, command, volumes)`), so swapping the import in `receive_vis.py`/`process_vis.py` is a one-line change — including writing the PVC manifest (`k8s/pvc.yaml`) and confirming it binds on minikube before any Job-creation code.
- Reviewed each draft iteration: caught a hostPath-volume bug (should mount the PVC by claim name, not a laptop-local path meaningless inside the cluster), a `backoff_limit=4` that would double-retry on top of Prefect's own task retries, a shell-vs-argv mismatch (`/bin/sh -c` vs `shlex.split`, to match `docker_runner`'s no-shell behavior), and a param name mismatch (`volume` vs `volumes`) that would have broken the "one-line import swap" the whole design depended on.
- Verified end-to-end against a real minikube cluster: PVC bound, a real Job ran to completion (`kubectl get jobs -w` showed `Complete 1/1`), and the output `.ms` was confirmed present inside the PVC via a debug pod.
- Diagnosed a real design gap this exposed: the PVC is cluster-local storage, not the project's local `./data` — wiring it in fully would also require moving `storage.py`'s disk scan, preview-artifact generation, and `remove_ms` to operate against the cluster-mounted volume. Decision (user-confirmed): ship `docker_runner` for the demo, keep `k8s_runner` as a proven-but-unwired design artifact, documented honestly in `README.md` and `documentation/notes.md`.
- Explained, for the "Extended scope" write-up: concrete advantages Kubernetes would offer over the shipped Docker path (cluster-scale concurrency, declarative infra, resource-aware scheduling, distributed storage, production parity with `KubernetesConfig`'s existing fields) — and the honest tradeoff that none of it mattered at this project's actual scale.
